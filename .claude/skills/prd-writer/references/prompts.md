# 需求采集 Prompt 模板

---

## Prompt 1：从会议记录提取需求

```
角色设定：
你是一位拥有 10 年经验的资深产品经理，擅长从混乱的会议讨论中提炼出清晰的业务需求。

任务背景：
我刚刚参加了一场产品需求讨论会议，会议录音已转为文字。现在需要你帮我从中提取出可落地的功能需求清单。

输入材料：
- 会议转写文稿（见上文）
- 项目背景补充：[在此粘贴：目标用户、业务场景、技术栈限制等]

输出要求：
1. **内容清洗**：去除所有寒暄、跑题、重复内容，只保留与产品功能相关的需求描述
2. **结构分类**：按以下维度组织需求
   - 【核心业务流程】：端到端的主流程（如：用户注册→登录→下单→支付）
   - 【用户端功能】：C端用户可见的功能模块
   - 【管理端功能】：B端/运营后台功能
   - 【技术需求】：性能、安全、兼容性等非功能性需求
3. **优先级标注**：用 🔴 P0（必须有）/ 🟡 P1（重要）/ 🟢 P2（优化项）标记
4. **痛点标记**：用 ⚠️ 标注客户反复强调或情绪激动时提到的需求
5. **格式规范**：使用 Markdown 无序列表，每个功能一行

示例输出格式：
## 核心业务流程
- 🔴 P0 用户注册流程：支持手机号+验证码注册，需校验手机号真实性
- 🔴 P0 ⚠️ 快速下单：客户强调必须 3 步内完成下单，不能有繁琐表单
```

## Prompt 2：结构化梳理 Feature List

```
角色设定：
你是一位拥有 B端/C端双重经验的产品架构师，擅长将零散需求整理为完整的功能地图。

任务：
我正在规划一个 [项目类型]，以下是初步需求清单：
[粘贴需求清单]

输出要求：
1. **模块化划分**：按业务模块组织（如：账号体系、首页、商品管理、订单流程、支付结算、个人中心、运营后台）
2. **功能三要素**：每个功能点必须包含
   - 功能名称：动宾结构（如：创建订单、导出报表）
   - 功能描述：一句话说清楚"用户可以做什么"（WHO + DO WHAT + FOR WHAT）
   - 优先级：P0（MVP 必须）/ P1（重要增强）/ P2（体验优化）
3. **逻辑完整性检查**：主动指出需求中可能缺失的环节，例如：
   - 有"加入购物车"但没提"购物车编辑/删除"
   - 有"用户注册"但没提"找回密码"
   - 有"生成订单"但没提"订单取消/退款"流程
4. **表格化输出**：使用 Markdown 表格格式

输出格式示例：
## 模块 1：用户账号体系
| 功能编号 | 功能名称 | 功能描述 | 优先级 | 备注 |
|---------|---------|---------|--------|------|
| U-01 | 手机号注册 | 用户通过手机号+验证码完成账号注册 | P0 | 需防刷机制 |
```

## Prompt 3：四角色反向推演审查

```
角色切换指令：
现在请切换为以下四个角色，分别对上述 Feature List 进行"挑刺"：

1. **技术负责人**：从技术实现难度、系统性能、安全风险角度提出 3 个尖锐问题
   示例："如果用户在支付过程中网络断开，订单状态如何处理？是否有幂等性设计？"

2. **挑剔的用户**：从操作便捷性、流程合理性角度提出 3 个质疑
   示例："为什么修改收货地址要跳转三个页面？能不能在订单确认页直接编辑？"

3. **运营负责人**：从数据分析、营销推广角度提出 2 个需求补充
   示例："是否有用户行为埋点？如何追踪营销活动的转化效果？"

4. **测试工程师**：从异常场景覆盖角度提出 2 个边界问题
   示例："如果用户重复点击提交按钮会怎样？是否有防重复提交机制？"

输出格式：
- 每个角色的问题单独列出
- 每个问题后面给出建议解决方案
- 标注哪些问题需要补充到 Feature List 中
```

## Prompt 4：需求优先级排序

```
角色设定：
你是一位经验丰富的产品总监，擅长在有限资源下做出正确的优先级决策。

任务：
以下是我整理的功能清单，请帮我进行优先级排序和 MVP 范围划定：
[粘贴功能清单]

评估维度（每个功能从 1-5 打分）：
1. **用户价值**：对核心用户体验的影响程度
2. **商业价值**：对营收/留存/增长的贡献
3. **实现成本**：开发工作量（人天）
4. **技术风险**：不确定性高低
5. **依赖关系**：是否被其他功能依赖

输出要求：
1. 使用 RICE 评分模型（Reach × Impact × Confidence / Effort）
2. 明确 MVP 范围（哪些是第一版必须有的）
3. 按优先级排序的功能列表
4. 建议的迭代节奏（MVP → V1.1 → V1.2）
```

## Prompt 5：快速生成完整 PRD（模式 D 专用）

```
角色设定：
你是一位拥有 10 年经验的资深产品经理 + 技术架构师，擅长快速将产品想法转化为专业、完整、可执行的需求文档。

任务背景：
用户已经有一个清晰的产品想法，需要直接生成完整 PRD，不需要来回讨论。

输入材料：
- 产品描述：[在此粘贴用户的原始描述]
- 产品形态：[Web App / 小程序 / 原生 App / 插件，如未指定则根据描述推荐]
- 团队规模：[Solo / 小团队 / 企业级，默认 Solo]

输出要求：
按以下 8 个章节顺序输出完整 PRD。每个章节独立、完整，信息不足处标 [待补充]。

---

## 第 1 章：产品概述

必须包含：
- 产品名称（如未提供，给出 3 个候选）
- 一句话定位：「[产品名] 是一款面向 [目标用户] 的 [产品类型]，帮助他们解决 [核心问题]，通过 [核心方式] 实现 [核心价值]」
- 核心目标（1-3 个可衡量的目标）
- 项目背景（为什么现在做这个产品）

---

## 第 2 章：用户与场景

必须包含：
- 目标用户画像（年龄、职业、技术水平、使用场景）
- 2-3 个典型使用场景（场景 → 问题 → 现有解决方案 → 我们的方案）
- 用户痛点和优先级排序

---

## 第 3 章：功能设计

必须包含：
- 功能清单（树状结构，标注优先级）：
  - 🔴 P0 核心（MVP 必须）
  - 🟡 P1 重要（增强体验）
  - ⚪ P2 规划（远期迭代）
- 核心功能流程图（Mermaid 语法）
- 界面结构说明

流程图使用 Mermaid 语法格式：
​```mermaid
graph TD
    A[开始] --> B[步骤1]
    B --> C{判断}
    C -->|是| D[步骤2]
    C -->|否| E[步骤3]
​```

---

## 第 4 章：技术设计

必须包含：
- 系统架构图（Mermaid graph 或 C4 语法）
- 核心模块说明
- 数据流说明
- 技术选型建议（根据产品形态和团队规模推荐）

---

## 第 5 章：交互与体验

必须包含：
- 用户操作流程（主流程 + 异常分支）
- 异常情况处理方案（网络错误、数据加载失败、权限不足等）
- 操作反馈规范（成功/失败/加载中/空状态提示文案）
- 关键页面的 ASCII 线框图

---

## 第 6 章：数据与接口

必须包含：
- 核心数据实体及字段规范（字段名/类型/必填/默认值/校验规则）
- 主要 API 接口列表（方法/路径/描述）
- 第三方服务依赖

---

## 第 7 章：项目规划

必须包含：
- MVP 范围（哪些功能在第一版）
- 建议迭代计划（MVP → V1.x → V2.x）
- 各阶段里程碑和验收标准

---

## 第 8 章：风险与约束

必须包含：
- 技术风险（不确定性最高的部分）
- 资源约束（时间/人力/预算）
- 已知限制
- 依赖风险（第三方服务/平台政策）

---

**通用原则：**
1. 所有流程图使用 Mermaid 语法
2. 表格使用 Markdown 表格格式
3. 宁可标 [待补充] 也不编造
4. 文档面向两个读者：开发者（技术规格）和产品决策者（业务逻辑）
5. 根据团队规模调整深度：
   - Solo/Vibe Coding：聚焦核心功能，文档简洁可执行
   - 小团队：补充交互细节和数据规范
   - 企业级：补充非功能性需求和风险评估
```
