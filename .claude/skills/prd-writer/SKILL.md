# PRD Writer — 通用产品需求文档撰写技能

把产品经理的核心思维封装成可执行的工作流，帮助任何有产品想法的人系统地把想法变成专业级需求文档。

**适用人群：** 有产品想法但不懂 PRD 写法的独立开发者、创业者、产品新人，以及需要规范化需求文档的团队。

**核心设计思路：**
- 先验证方向，再展开细节 —— 方向错了，细节都是浪费
- 两阶段交付：概念版对齐方向 → 落地版完整细节
- 三视角诊断：用户需求 → 商业可行 → 技术落地
- 自动补盲区：交互细节、状态机、数据规范、文案风格 —— 主动补，不等用户问
- 模块化流水线：需求采集 → 诊断 → 文档 → 质检 → 原型 → 导出，每步可独立使用

---

## 第零步：识别用户阶段与模式选择

> 启动前的必要检查。先确认用户当前的状态，再进入对应模式。

**先问用户：**
> "在开始之前，能先跟我说说你的情况吗？你是有个新想法想写需求文档，还是已经有文档想让我检查/改进/补充？"

| 用户的情况 | 进入模式 |
|-----------|---------|
| 想直接从一段描述生成完整 PRD，不需要来回讨论 | **→ 模式 D：快速生成** |
| 有想法，还没有文档，想要引导式产出 | **→ 模式 A：从零引导** |
| 已有一份需求文档，想检查/改进 | **→ 模式 B：评估 + 改进** |
| 已有文档，想追加新需求或补充细节 | **→ 模式 C：增量融合更新** |
| 只想生成原型 / 只想导出文档 | **→ 直接跳转到对应阶段** |

**模式 A 的前置判断：**

| 用户的回答 | 判断 | 处理 |
|-----------|------|------|
| 能说出「谁的什么问题，用什么方式解决」 | ✅ 有核心逻辑 | 进入第一步 |
| 描述模糊但有方向，如「我想做个帮人记账的 App」 | ⚠️ 有苗头 | 追问引导明确核心逻辑 |
| 完全没有方向，如「我想做个 App，你帮我想做什么」 | ❌ 不适合 | 温和说明本工具适合已有初步想法的用户 |

## 模式 A：从零引导，两阶段交付

```
需求采集 → 三视角诊断 → 概念版(方向对齐) → 落地版(完整细节) → 质量检查 → [可选]原型/导出
```

### 第一步：需求采集

根据用户提供的信息来源，选择合适的采集方式：

#### 来源 1：用户口头描述

直接进入三视角诊断（第二步）。

#### 来源 2：会议记录 / 聊天记录

使用结构化提取流程，将杂乱讨论提炼为清晰需求：

```
## 核心业务流程
- 🔴 P0 功能名称：功能描述

## 用户端功能
- 🟡 P1 功能名称：功能描述

## 管理端功能
- 🟢 P2 功能名称：功能描述
```

提取要求：
- 去除寒暄、跑题、重复内容
- 按「核心业务流程 / 用户端 / 管理端 / 技术需求」分类
- 用 🔴 P0（必须有）/ 🟡 P1（重要）/ 🟢 P2（优化）标注优先级
- 用 ⚠️ 标注反复强调的需求痛点

详细 prompt 模板见 [references/prompts.md](references/prompts.md)

#### 来源 3：已有零散需求列表

整理为结构化 Feature List，进行完整性检查（如有"加购物车"但没"购物车编辑"）。

模板见 [references/feature-list-template.md](references/feature-list-template.md)

---

### 第二步：三视角诊断（方向对齐前的必做项）

在写任何文档之前，先从三个视角快速诊断。**每次只问 1-2 个问题，像对话一样推进**，不要一次抛出所有问题。

#### 视角 1：用户角度 —— 这个需求真实存在吗？

- 你的目标用户现在是怎么解决这个问题的？
- 现有方式有什么不够好？你的产品好在哪里？
- 有没有跟真实用户聊过这个痛点？

#### 视角 2：商业角度 —— 这件事值得做吗？

- 怎么赚钱？对你有什么商业价值？
- 市场上有类似产品吗？你和他们最大的差异是什么？
- 目标用户规模大概多少？

#### 视角 3：开发角度 —— 这件事做得出来吗？

- 最核心的技术能力现在有吗，还是依赖第三方？
- 有没有实现起来最难的部分？
- 如果先做 MVP，哪些功能是必须有的？

#### 产品形态选择

如果用户没有明确形态，根据三视角信息主动给出推荐：

| 形态 | 适合场景 | 核心优势 | 主要限制 |
|------|---------|---------|---------|
| **网页 Web App** | 功能复杂、大屏操作、B 端工具 | 开发最快，跨平台，易分享 | 移动端体验弱，不能离线 |
| **微信小程序** | 中国用户为主、社交传播 | 微信生态流量，无需下载 | 功能受平台约束 |
| **原生 App** | 强依赖设备能力、高频使用 | 体验最好，推送稳定 | 开发成本高，审核周期长 |
| **AI Skill / 插件** | 增强已有工具，非独立产品 | 成本极低，利用宿主流量 | 依赖平台，自由度受限 |

**推荐框架：** 目标人群在哪里 → 核心功能要求 → 团队现状 → MVP 优先原则

**多形态并存策略：** 有时候答案不是非此即彼——比如「先做网页版验证需求，跑通后再出 App」是完全合理的路径。如果这是最优解，明说出来，并在概念文档里写清楚分阶段的形态策略。典型路径：网页版验证 → 小程序获客 → 原生 App 深度体验。

> **诊断原则：** 三个视角都要过，不追求完美答案。某个视角卡壳时温和指出，帮用户一起想，不要跳过。诊断完成后口头总结方向，让用户确认。

### 第三步：输出【第一版 · 产品概念文档】

**唯一目的：对齐方向。** 保持简洁，不展开细节。

模板见 [references/prd-template-concept.md](references/prd-template-concept.md)

输出后询问：*"这份概念版符合你的预期吗？方向、定位、目标人群有没有哪里不对？没问题了再展开细节。"*

- 用户满意 → 进入第四步
- 用户觉得不对 → 修改概念版，重复直到对齐
- **不要因为用户说「差不多」就跳过 —— 要明确确认「方向认可了」**

---

### 第四步：输出【第二版 · 落地需求文档】

> ⚠️ **只有概念版得到明确确认后，才能进入这一步。**

目标：让文档能被 AI 或开发者直接拿去实现。信息不足时标 `[待补充]`，不编造。

模板见 [references/prd-template-full.md](references/prd-template-full.md)

文档结构：

1. **产品概述** — 从概念版继承
2. **目标用户与使用场景** — 展开画像 + 2-3 个典型场景
3. **核心用户动线** — Mermaid 流程图（主流程 + 异常分支）
4. **功能清单** — 树状结构，🔴 核心 / 🟡 重要 / ⚪ 规划
5. **关键页面布局线框图** — ASCII 字符画，标注区域名称和作用
6. **功能详细描述** — 每个 🔴 核心功能独立一节：
   - 功能描述 + 触发条件
   - 交互细节（操作反馈/危险操作确认/空状态引导/失败引导）
   - 状态清单（默认/加载中/成功/失败/禁用/空状态）
   - 边界条件（空内容/超长/网络异常/无权限/并发/格式不符）
   - 数据规范（字段名/类型/长度/必填/默认值/校验规则）
7. **文案规范** — 双受众：面向开发的字段说明 vs 面向用户的产品文案
8. **非功能性需求** — 性能/权限/兼容性/安全/存储
9. **待确认问题** — 标明影响范围

线框图指南见 [references/wireframe-guide.md](references/wireframe-guide.md)

---

### 第五步：质量检查

完成落地版后，以四个角色视角审视：

1. **技术负责人**：并发/幂等/异常恢复/数据一致性/安全/性能
2. **挑剔用户**：操作步骤/表单字段/错误提示/加载状态/撤销
3. **运营负责人**：埋点/转化追踪/用户分层/运营工具/数据导出
4. **测试工程师**：边界值/并发操作/网络异常/设备兼容/权限边界

详细清单见 [references/quality-checklist.md](references/quality-checklist.md)

**输出格式：** 总体评分（10分制）+ 分层问题列表 + 建议修复方案

### 第 5.5 步（可选）：润色优化

> 灵感来自 prd-writer-main 的「拼装后润色」机制。

落地版生成后，对完整文档做一次统一润色：

1. **逻辑连贯性**：检查各章节之间是否有矛盾或跳跃（如功能清单和详细描述是否一致）
2. **术语统一**：确保产品名称、功能名称、用户角色等术语全文一致
3. **格式统一**：标题层级、列表风格、表格结构是否统一
4. **完整性校验**：每个 🔴 核心功能是否都有状态清单、边界条件、数据规范
5. **交叉引用**：用户动线中提到的功能，是否在功能清单和详细描述中都有对应

润色时不要改变用户确认过的方向和核心逻辑，只做一致性优化。

## 模式 D：快速生成（一步到位）

> 适用于用户已有清晰想法，不想来回讨论，只想直接拿到完整 PRD。

**适用场景：**
- 用户说"帮我把这段话直接生成完整PRD"
- 用户提供了详细的产品描述，不需要诊断引导
- 时间紧迫，需要快速出文档

**工作流程：**

```
用户描述 → 一次性生成 8 个章节 → 拼装 → 润色 → 输出
```

**固定 8 章节架构：**

| 章节 | 内容 |
|------|------|
| 1. 产品概述 | 产品名称、定位、核心目标、项目背景 |
| 2. 用户与场景 | 目标用户画像、核心使用场景 |
| 3. 功能设计 | 功能列表（带优先级）、功能流程图、界面结构 |
| 4. 技术设计 | 系统架构图、模块说明、数据流 |
| 5. 交互与体验 | 用户流程、异常情况与反馈 |
| 6. 数据与接口 | 主要接口列表、第三方依赖 |
| 7. 项目规划 | MVP 范围、迭代计划 |
| 8. 风险与约束 | 技术风险、资源约束、已知限制 |

**生成要求：**
- 所有流程图使用 Mermaid 语法
- 每个章节独立生成，最后按顺序拼装
- 拼装后做一次整体润色（统一术语、检查逻辑连贯性）
- 信息不足处标 `[待补充]`

快速生成 prompt 模板见 [references/prompts.md](references/prompts.md) 中的「Prompt 5：快速生成完整 PRD」

## 模式 B：评估 + 改进已有文档

收到用户文档后，按三层 checklist 逐项检查：

### 方向层
- [ ] 有明确的目标用户和核心痛点
- [ ] 有清晰的一句话产品定位
- [ ] 有明确的产品形态及选型理由
- [ ] 有商业价值或变现逻辑
- [ ] 有明确的「不做什么」边界
- [ ] 三视角都有基本答案

### 结构层
- [ ] 有核心用户动线（流程图或文字描述）
- [ ] 有结构化功能清单（带优先级）
- [ ] 有关键页面布局线框图
- [ ] 每个核心功能有独立详细描述

### 细节层
- [ ] 每个交互元素列出全部状态（含加载/失败/禁用/空状态）
- [ ] 边界条件已覆盖
- [ ] 有交互细节（操作反馈、危险操作确认等）
- [ ] 有数据规范（字段名、类型、长度、必填、默认值）
- [ ] 有面向终端用户的文案规范，且与开发文档分开

**输出：** 总体评分（10分）+ 分层问题列表 + 询问用户处理方式

## 模式 C：增量融合更新

**核心原则：融合而不是覆盖，更新而不是重写。**

### 操作步骤

1. 让用户提供现有文档（粘贴或告知位置）
2. 明确想追加/修改的内容
3. 定位影响范围（功能清单 / 用户动线 / 功能描述 / 数据规范）
4. 执行融合 —— 不删除原有内容，新内容融入对应位置
5. 用 `【本次更新】` 标注所有改动
6. 融合后检查：动线是否同步 / 新字段是否补了交互细节和边界条件 / 功能清单和详细描述是否一致

## 通用原则（每次生成都必须遵守）

**1. 分阶段，不跳跃**
概念版没确认前，不展开落地细节。顺序：核心逻辑验证 → 三视角诊断 → 概念版对齐 → 落地版展开。

**2. 三视角都要过**
用户/商业/开发三个角度都必须有基本清晰的答案。某个视角明显空白，指出来一起想。

**3. 帮小白补盲区**
交互细节、数据规范、文案规范 —— 主动补，不等用户问。

**4. 双受众意识**
文档有两个读者：AI/开发者（需要技术规格）和终端用户（需要好的产品文案），两者分开定义。

**5. 融合不覆盖**
追加需求时不丢失原有内容，用 `【本次更新】` 标注改动。

**6. 宁可标 [待补充] 也不编造**
信息不足时明确标出，不用模糊语言糊弄。

**7. 用图和表格代替纯文字**
用户动线用 Mermaid 流程图，状态清单用表格，功能清单用树状结构，页面布局用 ASCII 线框图。

**8. 适配不同场景的深度**
- Solo 开发者 / Vibe Coding：聚焦核心功能，文档简洁可执行
- 小团队协作：补充用户动线、交互细节、数据规范
- 企业级：完整文档 + 非功能性需求 + 迭代规划 + 风险评估
