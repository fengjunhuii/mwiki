# Markdown 文档规则

## 1. 适用范围

- 适用于项目内所有 Markdown 文档：需求、设计、开发说明、问题分析、评审材料、测试说明。
- 默认使用中文简体，专业术语首次出现时可附英文原文（如“可追溯性 Traceability”）。
- 一个文件只聚焦一个主题，避免把需求、设计、测试结果混杂在同一文档。

## 2. 文档结构约定

- 每个文件必须且仅有一个一级标题（`#`），标题应准确表达主题。
- 推荐固定结构：`背景/目标` -> `范围` -> `方案或内容主体` -> `风险与边界` -> `验证方式` -> `附录`。
- 标题层级按顺序递进，不跳级（例如 `##` 后只能进入 `###`）。
- 段落尽量短小，单段建议不超过 8 行，长段落拆分为小节或列表。

## 3. 内容与表达规范

- 使用客观、可执行语句，避免“可能”“大概”“看情况”等模糊表述。
- 描述规则时优先“必须/应当/禁止”，便于审查与落地。
- 不使用 emoji 和口语化语气，保持技术文档专业性。
- 涉及结论时必须有依据（数据、日志、代码路径、测试结果之一）。

## 4. 代码块与命令规范

- 所有代码块必须标注语言，如 `cpp`、`bash`、`json`、`yaml`、`text`。
- 命令示例需可复制执行，避免省略关键参数或上下文。
- 引用项目内路径、函数、类、配置键时，统一使用反引号包裹。
- 大段日志默认用 `text` 代码块，并在前文说明日志来源与时间。

## 5. 链接与路径规范

- 文档之间优先使用相对路径链接，例如 `../docs/xxx_design.md`。
- 禁止使用本地绝对路径（如 `C:\...`）作为长期文档引用。
- 外部链接必须使用可访问的完整 URL，并尽量附一句用途说明。
- 同一文档内引用章节时，优先使用锚点链接保持可导航性。

## 6. 图片、图表与附件规范

- 图片必须有上下文说明，禁止“只贴图不解释”。
- 图/表标题建议使用“图 x-xx”“表 x-xx”风格，便于评审引用。
- 引用附件（docx/xlsx/pdf）时注明来源、版本和用途。
- 避免嵌入超大二进制内容；优先引用相对路径并在仓库内统一管理。

## 7. 表格与清单规范

- 表格用于对比、映射、检查项，不用于承载长段说明文字。
- 清单项应可验证，推荐使用“动作 + 对象 + 条件”格式。
- 评审/验收清单建议采用复选框格式（`- [ ]`），便于状态追踪。

## 8. 变更记录与可追溯

- 关键文档（需求、设计、评审、验证）建议包含版本与更新时间。
- 当文档结论依赖代码实现时，需给出相关模块或文件路径。
- 当文档结论依赖测试结果时，需说明测试范围、环境和结果摘要。
- 已存在文档必须采用“先读取、后增量更新”流程，禁止先删除再重写。
- 未经用户明确授权，禁止删除需求/设计/评审/测试文档文件。

## 9. 推荐模板（可按需裁剪）

```markdown
# 文档标题

## 1. 背景与目标
## 2. 范围与非范围
## 3. 方案/设计/实现说明
## 4. 风险与边界条件
## 5. 验证与验收标准
## 6. 变更记录
## 7. 附录（链接、术语、参考）
```

## 10. 提交前自检

- [ ] 仅保留一个一级标题，层级无跳级
- [ ] 路径/函数/类名均使用反引号
- [ ] 代码块均声明语言类型
- [ ] 文档链接为相对路径或有效 URL
- [ ] 无 emoji、无模糊表述、无明显错别字
- [ ] 关键结论可追溯到代码、日志或测试证据
- [ ] 已存在文档采用增量更新（未先删后写）
