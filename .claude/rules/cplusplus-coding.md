# C++ 编码规范 V2.1

本规范在生成或修改 C/C++ 代码时**强制遵循**，同时作为人工评审与 Code Review 的判据。目标：生成的代码必须可验证、可审计、可落地，遵循团队统一风格。

**本文件为编码规范本体**：承载适用范围、语言子集、冲突优先级、Top 10 快查表与规则条款（§1–§17）；**不依赖任何外部文档**即可对代码进行约束。流程/门控/工作流类内容（若项目需要）由其他文件或 skill 承担，与本规范解耦。

## Top 10 高危 MUST 快查表（高频违反）

| 编号 | 规则 | 典型错误 | 正确做法 |
| --- | --- | --- | --- |
| MUST-9.6.3 | 并发锁必须 RAII | 裸 `pthread_mutex_lock(&m); ... pthread_mutex_unlock(&m);` | 使用 `CScopedLock` / `std::lock_guard` |
| MUST-16.1.4 | `const` 正确性 | `(MsgPack_t *)pConstHead`（丢弃 `const`） | 调整接口使其 `const` 正确，或显式复制 |
| MUST-3.2.5 | 参数布局 | 函数声明/定义参数超过 2 行；**新建文件仿老代码多行对齐** | 新建文件默认单行；超出 §3.5.1 120 字符上限时才拆两行 |
| MUST-8.3.1 | 参数校验 | 函数体内直接解引用入参 | 入口统一 `if (NULL == pData) { return ERR_INVALID; }` |
| MUST-9.1.5 | 释放后置 NULL | `free(p);` 结束即离开作用域 | `free(p); p = NULL;` |
| SHOULD-16.2.3 | 单一退出清理 | 多 `return` 泄漏资源 | `do { ... } while (0)` 模式 |
| MUST-7.3.5 | Yoda 条件 | `if (x == NULL)` | `if (NULL == x)` |
| MUST-3.2.3 | 必带大括号 | `if (x) return;` | `if (x) { return; }` |

| MUST-6.2 | 命名空间 | 未经用户确认新开 `namespace foo` | 未经用户明确指令，禁止**新增**命名空间（既有命名空间正常使用） |

## 0. 协议总则

### 0.1 适用范围

- **适用文件**：`*.h`、`*.hpp`、`*.c`、`*.cpp`、`*.cc`、`*.cxx`（新增/重构/修复代码）。
- **非适用**：纯第三方代码镜像；老代码无修改需求时可保持原格式。

### 0.2 规则级别

- `MUST`：强制，必须修正。
- `SHOULD`：推荐，若偏离必须在代码注释中按 §17 提供的**例外注释模板**显式记录（含规则编号、原因、评审人、复核点）。
- `MAY`：可选。

### 0.3 语言子集（受限 C++11）

精确的"允许 / 禁止 / 审批"清单。未列入的 C++11 特性默认按"审批"处理，使用前必须经团队确认。

| 特性 | 状态 | 说明 |
|---|---|---|
| `const` / `NULL` / 显式类型 | **允许**（推荐） | 优先使用 |
| `nullptr` | **允许**（仅 C++） | 仅在 `*.cpp/*.cc/*.cxx/*.hpp/*.h` 等按 C++ 编译的文件中允许；`*.c` 中仍使用 `NULL`（C 不支持 `nullptr`）。 |
| `auto` | **禁止** | 显式类型 |
| 范围 `for`（`for (auto &x : c)`） | **禁止** | 用显式迭代器 / 下标循环 |
| `std::unique_ptr` / `shared_ptr` | **禁止** | 老规范要求不使用智能指针进行内存管理 |
| `std::optional` / `variant` / `any` | **禁止** | 老规范要求不使用这些类型安全替代方案 |
| `#pragma once` | **禁止** | 统一用 `ifndef / define / endif` 宏保护（见 §1.2.1） |
| STL 容器 | **允许** | 老规范允许必要的 STL 容器与标准算法 |

### 0.4 冲突优先级

本规范 > 团队约定 > 个人偏好；改既有代码时局部一致性优先；第三方交互允许在 `extern "C" { ... }` 内沿用其风格。

### 0.5 项目内部依赖与示例约定

- 本规范在部分条款与示例中引用项目内部公共头文件：
  - `streamaxtype.h`：基本类型重定义（`xint32_t` / `xuint8_t` / `xtime64_t` 等，见 §12.1.1）。
  - `streamaxerr.h`：接口级错误码（`ERR_OK` / `ERR_INVALID` / `ERR_ALLOC` 等，见 §8.2.3、§16.2.1）。
  - `CScopedLock` / `RM_CBB_LOG_XXX`（如 `BUS_LOG_XXX`）：优先参考项目既有并发与日志封装（见 §9.6.3、§14.3）。
- 这些文件/符号为**项目基础设施**，不视为"外部规范文档"。本规范自身不依赖任何外部规则或流程文档即可对代码进行约束；落地到具体代码时仍须复用上述基础设施。
- 规范示例中为聚焦规则本体，部分片段使用 `int`/`char` 等原始类型与 `ERR_XXX` 占位错误码；真实代码必须改为 §12.1.1 所列重定义类型与 `streamaxerr.h` 中的正式错误码。

## 1. 文件组织

### 1.1 版权与版本声明

- `[MUST-1.1]` 每个头文件（`*.h`/`*.hpp`）开头须包含版权声明块（含：版权信息、文件名、摘要、当前版本、作者、完成日期、版本历史）。
- `*.c`/`*.cpp`/`*.cc`/`*.cxx` 实现文件的版权声明块**默认省略**。

```cpp
/*
 * Copyright (c) 2018, 深圳市锐明技术股份有限公司
 * All rights reserved.
 *
 * 文件名称：filename.h
 * 摘    要：简要描述本文件的内容
 * 当前版本：1.1
 * 作    者：作者/修改者
 * 完成日期：YYYY年MM月DD日
 */
```

### 1.2 头文件结构

- `[MUST-1.2.1]` 头文件必须使用 `ifndef/define/endif` 防重复包含；宏名基于源代码树全路径（`_<PATH>_<FILE>_H__`），`#endif` 后必须注释对应宏名；标准库用尖括号，项目内头文件用双引号。
- `[MUST-1.2.2]` 头文件只存放声明，不放定义；禁止在头文件中定义函数体（含类成员函数）。例外：`inline` 函数、模板函数必须在头文件中定义。
- `[MUST-1.2.3]` 头文件禁止 `extern` 声明全局变量；不提倡全局变量，必须时封装为函数访问或常量。
- `[MUST-1.2.4]` 头文件按"实际使用处"引入，降低编译耦合；实现文件需要的头文件放在 `*.cpp`，不一律上移到 `*.h`。
- `[SHOULD-1.2.5]` 能用前置声明就不要 `#include`：`*.h` 中仅使用某类型指针/引用时优先 `class CFoo;` / `struct Bar_t;`，仅需要完整类型（成员、继承、`sizeof`、按值）时才 `#include`。
- `[SHOULD-1.2.6]` 头文件包含顺序：对应源文件头 → 本项目头 → 第三方库头 → 标准库头，组间空行分隔。
- `[MUST-1.2.7]` 头文件中的 `#define/enum/struct/typedef/using` 一律放在 `#include` 之后、`class` 定义之前；**禁止在类体内新增任何类型定义（含嵌套 `enum`/`struct`/`typedef`/`using`/嵌套 `class`）**。

### 1.3 定义文件结构与编码

- `[MUST-1.3.1]` `*.cpp`/`*.c` 由两部分组成：头文件引用 → 实现体；若保留版权版本声明块，则置于文件最开头，且应与 §1.1 的字段保持一致。
- `[MUST-1.4.1]` 新文件统一使用 UTF-8（无 BOM）；老文件做较大改动时建议同步转为 UTF-8。

## 2. 命名规则

### 2.1 通用原则

- `[MUST-2.1.1]` 标识符可望文知意：使用英文单词或其组合，禁止汉语拼音；遵循 `min-length && max-MESSAGErmation`（`maxValue` 优于 `maxValueUntilOverFlow`）；单字符名（`i`/`j`/`k`/`x`/`y`/`z`）仅限函数内小范围局部变量。
- `[MUST-2.1.2]` 同一作用域不出现同名标识符；禁止局部变量与全局变量重名（即便作用域不同）；禁止成员变量与局部变量重名。
- `[MUST-2.1.3]` 变量名使用"名词"或"形容词+名词"：`value`、`oldValue`、`newValue`、`minValue`、`maxValue`。
- `[MUST-2.1.4]` 互斥语义使用正确反义词：`minValue`/`maxValue`、`SetValue`/`GetValue`、`Open`/`Close`。
- `[SHOULD-2.1.5]` 避免用数字编号命名：`value1`/`value2` 改用 `numErrors`/`numCompletedConnections`；仅逻辑确需编号时使用。

### 2.2 命名风格总表

#### `[MUST-2.2.1]` 标识符前缀/后缀与大小写风格必须符合下表

| 类别 | 风格 | 前缀/后缀 | 示例 |
|---|---|-----|---|
| 函数名 | 大驼峰 | 无 | `RegisterMsg`、`CalculateTotal` |
| 类名 | 大驼峰 | `C` 开头（既有项目风格） | `CHddManager`、`CStreamax` |
| 结构体名 | 大驼峰 | `_t` 结尾 | `UrlTableProperties_t` |
| 命名空间 | 大驼峰 | 无 | `Common`、`Streamax` |
| 枚举类型 | 大驼峰 | `e` 开头 | `eUrlTableErrors` |
| 局部变量 | 小驼峰 | 无 | `errorCount` |
| 类成员变量 | 小驼峰 | `m_` 前缀 | `m_userId`、`m_testResult` |
| 全局变量（尽量少用） | 小驼峰 | `g_` 前缀 | `g_muteFlag` |
| 静态变量（尽量少用） | 小驼峰 | `s_` 前缀 | `s_validCount` |
| 宏、枚举值、常量 | 全大写 | 下划线分隔 | `MAX_BUFFER_SIZE`、`ERROR_OUT_OF_MEMORY` |

- `[MUST-2.2.2]` 指针变量命名统一形态：**局部变量 / 函数参数** = `p` + 大驼峰（`pData`、`pMsgBuf`、`pOutBuf`）；**类成员指针** = `m_p` + 大驼峰（`m_pData`、`m_pBuf`）；**全局指针**（尽量不用） = `g_p` + 大驼峰。禁止使用 `p_xxx` / `p_Xxx` 这类下划线写法；禁止使用裸单字母 `p` / `pp` 作为公共接口参数名。`this`、标准库返回的迭代器等外部符号不强求改名。输出参数指针用 `pOutXxx` 形式表达数据流向（见 §8.1.2）。
- `[MUST-2.2.3]` 枚举首值必须显式赋值；非递增处必须显式赋值（展开见 `[MUST-16.3.2]`）。

## 3. 代码风格与排版

### 3.1 空行

- `[MUST-3.1.1]` 每个类声明后、每个函数定义结束后加空行。
- `[MUST-3.1.2]` 函数体内逻辑密切语句之间不加空行；其他地方加空行分隔逻辑段落。

### 3.2 代码行

- `[MUST-3.2.1]` 一行代码只做一件事：一行只定义一个变量，只写一条语句。
- `[MUST-3.2.2]` `if`、`for`、`while`、`do` 等语句自占一行，执行语句不得紧跟其后。
- `[MUST-3.2.3]` `if`、`for`、`while`、`do`、`else` 分支**一律加花括号 `{}`**，即使只有一条语句（包括单行 `return`/`break`/`continue`）。省略 `{}` 后新增语句会误入分支外。
- `[MUST-3.2.4]` 变量定义与首次使用就近，就近原则初始化。
- `[MUST-3.2.5]` 函数调用/声明/实现参数排版遵循"单行优先，最多两行"：函数调用、声明、定义在可读范围内时优先单行；**当单行超过 §3.5.1 的 120 字符上限**时必须换行，整体（从函数名到结尾 `)` / `);` / `{`）最多两行；除编译宏/长字符串字面量/链式调用等客观限制，不得拆分为三行及以上。

```cpp
ret = BuildPayload(1, 0, 0x00, 20, text, payload);                       // 单行
ret = BuildPayload(1, 0, 0x00, 20,
                   reinterpret_cast<const char *>(pText), payload);       // 两行
```

- `[MUST-3.2.6]` 未使用参数必须"先判断再处理"，禁止无脑改写：禁止不做判断就"删参数名/删参数/改签名"（可能导致声明与定义不一致、覆写关系破坏或跨模块编译失败）；先判断函数约束（`virtual/override`、回调接口、对外 API）→ 再选最小改动方案；签名受约束时保持签名不变，禁止使用注释参数名。
- `[MUST-3.2.7]` 禁止使用 `(void)param;` 方式处理未使用参数。

### 3.3 空格

- `[MUST-3.3.1]` 关键字后留空格（`const`、`virtual`、`inline`、`case`、`if`、`for`、`while`、`return`）。
- `[MUST-3.3.2]` 函数名紧跟 `(`；`(` 向后紧跟，`)`/`,`/`;` 向前紧跟（紧跟处不留空格）。
- `[MUST-3.3.3]` `,` 之后留空格；`for` 行内 `;` 之后留空格。
- `[MUST-3.3.4]` 二元操作符前后加空格（`=`、`+=`、`>=`、`+`、`*`、`&&`、`<<` 等）；一元操作符前后不加空格（`!`、`~`、`++`、取地址 `&`）。
- `[MUST-3.3.5]` `[]`、`.`、`->` 前后不加空格。

### 3.4 缩进与花括号

- `[MUST-3.4.1]` 默认 4 空格缩进；Tab 宽度设为 4 空格。
- `[MUST-3.4.2]` 预处理指令无嵌套从行首开始；有嵌套时与 `{}` 对齐。
- `[MUST-3.4.3]` 花括号 `{`/`}` 独占一行并同列（Allman 风格），与引用它们的语句左对齐；块内代码在 `{` 右 4 空格处对齐。

**例外（同行花括号）**：满足以下**全部**条件时，允许 `{` 与语句同行；该 80 字符为"同行花括号"专用收紧阈值，不替代 §3.5.1 的 120 字符行宽上限：

- 块内仅一条简单语句（`return` / `break` / `continue` / `goto` / 简单赋值）；
- 整行（含花括号与分号）≤ 80 字符；
- 场景限定二选一：(a) `if`/`else` 入口校验 + early-return；(b) `switch/case` 的 `case X: { stmt; } break;`。

```cpp
if (NULL == pData) { return ERR_INVALID; }                   // 允许
case eDEV_GATEWAY: { flag = 1; } break;                      // 允许

if (cond)                                                     // 默认：Allman
{
    DoA();
    DoB();
}
```

### 3.5 长行

- `[SHOULD-3.5.1]` 代码行长度控制在 120 字符以内。例外：注释中的长命令/URL、少量长路径、头文件保护宏。
- `[MUST-3.5.2]` 长表达式在低优先级操作符处拆分，操作符放在新行之首。

```cpp
if ((veryLongerVariable1 >= veryLongerVariable12)
    && (veryLongerVariable3 <= veryLongerVariable14))
{
    DoSomething();
}
```

### 3.6 修饰符位置

- `[MUST-3.6.1]` `*` 和 `&` 紧靠变量名；`int *x, y;` 避免 `y` 被误认为指针。

## 4. 注释规范

### 4.1 通用原则

- `[MUST-4.1.1]` 全部使用中文注释。
- `[MUST-4.1.1]` `/* ... */` 用于块注释。
- `[MUST-4.1.1]` `//` 用于单行注释（后空一格）。
- `[MUST-4.1.2]` 注释描述**为什么**而非**是什么**；不写流水账、不直译代码。
- `[MUST-4.1.3]` Interface 层对外 API 接口的注释说明必须遵循 doxygen 文档系统规则，以便根据特定批注转换成 HTML 说明文件。
- `[MUST-4.1.4]` doxygen 注释指令使用 `\` 或 `@` 作为前缀；为统一风格，项目内默认统一使用 `@`（JavaDoc 风格）标记 doxygen 命令。

### 4.2 注释对象要求

| 规则 | 注释对象 | 要求 |
|---|----|---|
| `[MUST-4.2.1]` | 文件 | 版权声明 + 文件内容概述（见 `[MUST-1.1]`） |
| `[MUST-4.2.2]` | 类 | 职责、用途、线程安全性 |
| `[MUST-4.2.3]` | 函数 | 声明处：功能/参数/返回值/异常；定义处：实现思路/算法/边界 |
| `[MUST-4.2.4]` | 变量 | 全局/常量注释含义；类成员注释用途；说明哨兵值（`NULL`、`-1`） |
| `[MUST-4.2.5]` | 实现 | 复杂/巧妙代码块前加注释；多重嵌套段落结尾加归属注释 |
| `[MUST-4.2.6]` | 字面量 | 调用处传入布尔/整数/`NULL` 必须注释或改用具名常量 |
| `[MAY-4.2.7]` | 待办 | `// TODO:` 并附负责人与日期 |
| `[MUST-4.2.8]` | 协议/格式化代码 | 协议帧、报文字段、保留位、校验算法、长度定义等必须注释"字段语义+取值/单位+边界条件"；禁止只写"拼包/解析"类空泛注释 |

## 5. 类设计与版式

### 5.1 版式原则

- `[MUST-5.1.1]` 采用"以行为为中心"版式，顺序：`public` → `protected` → `private`。
- `[MUST-5.1.2]` 访问修饰符缩进 1 个 Tab（4 空格）。
- `[MUST-5.1.3]` 除第一个修饰符外，其他修饰符前空一行。

```cpp
class A
{
public:
    void Func1(void);

protected:
    void InternalFunc();

private:
    int   i;
    float x;
};
```

### 5.2 类成员初始化

- `[SHOULD-5.2.1]` 成员声明同时初始化；类型与变量名分别对齐。

```cpp
int  m_value    = 0;
char m_name[32] = {0};
```

### 5.3 继承

- `[MUST-5.3.1]` 有派生类的基类必须声明虚析构函数；否则通过基类指针 `delete` 派生类对象时会内存泄漏。
- `[SHOULD-5.3.2]` 构造函数避免写复杂业务逻辑：构造失败难以传递错误；复杂初始化用独立 `Init()` 返回错误码。

## 6. 命名空间

- `[MUST-6.1]` 命名空间不添加额外缩进层次，结束 `}` 后加注释 `// namespace <name>`。
- `[MUST-6.2]` 未经用户明确指定，禁止**新增**任何命名空间（含具名 namespace）。本规则仅约束"新建命名空间层级"；对项目中既有命名空间（如 `Common`、`Streamax`）正常沿用，不得以"整理代码""避免冲突""个人风格"等理由自行引入新层级。确需新增时必须先获得用户明确指令并在评审说明中写明原因与影响范围。
- `[MUST-6.3]` 未经用户明确指定，禁止新增匿名命名空间（`namespace { ... }`）；文件内可见性控制优先沿用既有风格。

```cpp
namespace Common
{
void Foo() { /* ... */ }
}  // namespace Common
```

## 7. 表达式与基本语句

### 7.1 运算符优先级

- `[MUST-7.1.1]` 混合不同优先级运算符必须加括号：相同操作符连用、一元操作符可不加；混合不同优先级、含位运算、含条件表达式时必须加。

```cpp
word = (high << 8) | low;              // 必须加
if ((a | b) && (a & c)) { ... }        // 必须加
x = (a * 3) + c + d;                   // 不同优先级必须加
x = (a == b) ? a : (a - b);            // 三目必须加
x = a + b + c;                         // 相同操作符可不加
```

### 7.2 复合表达式

- `[MUST-7.2.1]` 禁止编写过于复杂的复合表达式。反例：`i = a >= b && c < d && c + f <= g + h;` 应拆分为多条语句或提炼子函数。
- `[MUST-7.2.2]` 禁止多用途复合表达式：`d = (a = b + c) + r;`（同时求 `a` 和 `d`）应拆为独立语句。
- `[MUST-7.2.3]` 禁止连续比较的数学写法：`if (a < b < c)` 等价于 `((a<b) < c)`，应写成 `if ((a < b) && (b < c))`。

### 7.3 `if` 语句与零值比较

- `[MUST-7.3.1]` **C++ `bool` 类型变量**直接比较：`if (flag)` / `if (!flag)`；禁止 `if (TRUE == flag)`、`if (1 == flag)`。判据按**声明类型**而非"语义"。
- `[MUST-7.3.2]` **任何非 `bool` 的整型变量**（含 `int` / `xint32_t` / `xuint8_t` / `typedef BOOL` 等）与常量比较必须采用显式值：`if (0 == value)`；禁止 `if (value)` 把整型当布尔。即使该变量在业务语义上"像布尔"，只要声明类型不是 C++ `bool` 就按本条处理。
- `[MUST-7.3.3]` **浮点变量**禁止直接等值比较，必须采用误差区间：`if ((x >= -EPSILON) && (x <= EPSILON))`；禁止 `if (x == 0.0)`。
- `[MUST-7.3.4]` **指针变量**必须与空指针常量显式比较：
  - **C 文件（`*.c`）**：仅允许 `NULL`：`if (NULL == p)` / `if (NULL != p)`；
  - **C++ 文件（`*.cpp/*.cc/*.cxx` 等）**：允许 `NULL` 或 `nullptr`：
    - `if (NULL == p)` / `if (NULL != p)`
    - `if (nullptr == p)` / `if (nullptr != p)`
  - 禁止 `if (p == 0)`、`if (p)`、`if (!p)`（不区分 C/C++）。
- `[MUST-7.3.5]` Yoda 条件：常量放在 `==`/`!=` 左侧。防止误写 `=`（`if (a = 5)` 不报错，但 `if (5 = a)` 会报错）。
- `[MUST-7.3.6]` `else if` 链末尾必须带 `else { /* no action */ }` 兜底。
- `[MAY-7.3.7]` 简单 `if/else/return` 可用三目：`return (condition ? x : y);`（禁止嵌套 `?:`）。

### 7.4 循环语句

- `[MUST-7.4.1]` 禁止在 `for` 循环体内修改循环控制变量（会导致循环行为不可预测）。
- `[MUST-7.4.2]` 循环变量采用"半开半闭区间" `[start, end)`：优先 `for (int x = 0; x < N; x++)`，避免 `x <= N - 1`。
- `[MUST-7.4.3]` 空循环体使用 `{}` 或 `continue`，不得用单独的 `;`（`while (condition);` 易误认为 do/while 的一部分）。
- `[SHOULD-7.4.4]` 多重循环：长循环置于最内层，减少 CPU 切换外层次数。
- `[SHOULD-7.4.5]` 循环体内固定逻辑判断移出循环；若循环次数 N 很大且 `condition` 不随循环变化，将 `if` 判断上移到循环外部，分别生成两个单一循环。
- `[SHOULD-7.4.6]` 循环内不变的对象在循环外定义，避免每次迭代的构造/析构开销。

### 7.5 `switch` 语句

- `[MUST-7.5.1]` 每个 `case` 结尾必须 `break`（除非有意 fall-through，须加 `// fall-through` 注释）。
- `[MUST-7.5.2]` 必须有 `default` 分支；即使无需处理，也写 `default: break;`，表明已考虑。
- `[SHOULD-7.5.3]` 每个 `case` 体用 `{}` 包裹。

```cpp
switch (type)
{
    case 1:  { flag = 1;   } break;
    default: { flag = 255; } break;
}
```

### 7.6 `goto` 语句

- `[MUST-7.6.1]` 禁止使用 `goto`。用 `do { ... } while(0)` 结构替代；已有 `goto` 遇到修改时同步重构。完整错误处理模板见 `[SHOULD-16.2.3]`。

## 8. 函数设计

### 8.1 参数

- `[MUST-8.1.1]` 参数书写完整，不得只写类型不写名字；无参函数用 `void` 填充（`void SetValue(int width, int height);` / `float GetValue(void);`）。
- `[MUST-8.1.2]` 参数顺序统一：写入目的端在前，只读源端在后；命名体现数据流向，禁止 `str1`/`str2` 等无方向歧义的命名。
- `[MUST-8.1.3]` 只读指针/引用参数必须 `const`，防止函数体内意外修改：`void StringCopy(char *strDest, const char *strSrc);`。
- `[SHOULD-8.1.4]` 大对象以 `const &` 传递，避免临时对象的构造/析构：`void Process(const CLargeObject &obj);`。
- `[MUST-8.1.5]` 禁止内联函数体**非空非注释语句行 > 10 行**（统计口径与 §8.5.2 一致，不含 `{` / `}` / 空行 / 纯注释）；包含循环/`switch` 一般不宜内联；虚函数、递归函数即使声明 `inline` 也未必真的内联。
- `[SHOULD-8.1.6]` 参数个数控制在 5 个以内；需要时封装为结构体。
- `[MUST-8.1.7]` 除打印函数外禁止使用不定参；`printf` 类不定参函数编译期类型检查弱，项目若提供类型安全的统一日志宏（例如 `RM_CBB_LOG_XXX`，例如 `BUS_LOG_XXX`）应优先使用。

### 8.2 返回值

- `[MUST-8.2.1]` 不得省略返回值类型；无返回用 `void`。
- `[MUST-8.2.2]` 函数名与返回类型语义一致（如 `getchar` 返回 `int` 而非 `char`）。
- `[MUST-8.2.3]` 正常值与错误标志分开返回：正常值用输出参数；错误标志用 `return`。接口函数错误码统一使用 `streamaxerr.h` 中的标准错误码；新接口必须遵循，老接口保持兼容。
- `[MUST-8.2.4]` 接收返回值类型须与函数返回类型保持一致。`time_t` 在 32/64 位平台字长不同，用 `int` 接收 64 位 `time_t` 会越界；用 `xuint32_t` 接收 `size_t` 同样风险。

### 8.3 入口检查与出口检查

- `[MUST-8.3.1]` 函数入口必须校验参数有效性：指针非空；长度、枚举在合法范围；校验显式入参也校验隐式依赖（全局变量、文件句柄等）。

```cpp
xint32_t Process(const xuint8_t *pData, xuint32_t uiLen)
{
    if ((NULL == pData) || (0U == uiLen)) { return ERR_INVALID; }
    // 主逻辑
    return ERR_OK;
}
```

- `[MUST-8.3.2]` 禁止返回指向函数内栈内存的指针或引用（局部 `char str[] = "hello"; return str;` — `str` 随函数返回销毁）。
- `[MUST-8.3.3]` 出口检查：所有返回分支必须确保内存已释放、文件/socket/互斥量已关闭/解锁、错误码语义明确。
- `[SHOULD-8.3.4]` 优先 early-exit，避免深嵌套：`if (!cond) { continue; }` / `if (!cond) { return ERR_XXX; }`。
- `[SHOULD-8.3.5]` 栈上大对象上限：**单个局部对象/数组不超过 4 KB**。线程栈默认仅 8 KB ~ 1 MB，嵌入式常被裁到 16 KB；超过 4 KB 改为堆分配并按 §9.1 / §9.5 管理；递归函数内不得定义 > 512 B 的局部聚合。若函数内多个局部大对象累计接近线程栈上限，也应按堆分配处理。

### 8.4 作用域

- `[MUST-8.4.1]` 变量放在最小作用域，并在声明时初始化：`while (const char *p = strchr(str, '/')) { str = p + 1; }`。
- `[SHOULD-8.4.2]` 本地辅助函数与工具接口默认不使用 `static`，仅在确有必要时使用。文件作用域辅助函数（`*.c/*.cpp` 顶层函数）默认不加 `static`；类内 `static` 成员函数默认也不新增，仅在"纯无状态工具函数且复用收益明确"时允许；任何新增 `static`（含局部 `static`）都应给出必要性说明，避免引入隐式状态与可测试性风险。

### 8.5 其他

- `[MUST-8.5.1]` 函数功能单一，不设计多用途函数。
- `[SHOULD-8.5.2]` 函数体不超过 80 行，超出时考虑提炼子函数。
- `[SHOULD-8.5.3]` 避免"记忆"函数：相同输入应产生相同输出；尽量不使用 `static` 局部变量。
- `[MUST-8.5.4]` 错误返回值语义清楚，不易被忽略或误解。

## 9. 内存与指针安全

> 本章为团队最核心的防错约束，所有指针相关规则统一归属于此。

### 9.1 内存生命周期

- `[MUST-9.1.1]` 谁申请谁释放：内存释放职责归属申请方；禁止依赖他人释放。
- `[MUST-9.1.2]` 释放函数与申请函数必须配套：`malloc` 配 `free`；`new` 配 `delete`；`new[]` 配 `delete[]`；所有返回分支均要释放，避免泄漏。
- `[MUST-9.1.3]` `new` 必须使用 `new(std::nothrow)` 形式：本项目已统一禁止 C++ 异常（见 §0.3 与 §16.2），`new` / `new[]` 必须使用 `new(std::nothrow)`，分配失败返回 `NULL`，由调用处按 §9.1.4 判空处理；禁止裸 `new` 依赖异常。例外：placement new、项目自定义分配器时，需在注释中引用本条并说明保证机制。

```cpp
xuint8_t *pBuf = new(std::nothrow) xuint8_t[uiLen];
if (NULL == pBuf) { return ERR_ALLOC; }
```

- `[MUST-9.1.4]` 申请内存后必须判空再使用（示例见 §9.1.3）；分配失败时所有后续访问必须短路。引申：任何资源（数据库连接、共享内存、文件句柄）申请后都必须进行有效性判断。
- `[MUST-9.1.5]` 释放后立即置 `NULL`，防止野指针与双重释放：`free(pBuf); pBuf = NULL;` / `delete[] pBuf; pBuf = NULL;`。**例外**：对象析构函数末尾释放成员指针后，可省略置空（对象即将消亡，置空无意义且会被编译器告警/删除）。
- `[MUST-9.1.6]` 禁止引用已释放的内存，典型错误：`char *c = s.c_str();`（`c_str()` 临时指针在 `s` 析构后失效）；正确做法是 `strncpy` 到本地缓冲并手动补 `\0`。
- `[MUST-9.1.7]` 结构体/数组/容器释放前必须释放其成员指针。顺序：从底层向上层依次释放（先 `free(pBuf->pInner)` 再 `free(pBuf)`），否则必然内存泄漏。

### 9.2 指针使用

- `[MUST-9.2.1]` 指针使用前必须判空：公共函数、共享工具函数入口拒绝 `NULL`，`if ((NULL == pData) || (0U == uiLen)) { return; }`。
- `[MUST-9.2.2]` 多指针指向同一内存时，释放后其余指针必须同步置空；对象生命周期难追踪时，应重新设计数据结构。
- `[MUST-9.2.3]` 禁止 `int` 与指针互相强制转换（`int i = (int)ptr;` / `void *ptr = (void *)s32Tmp;` 均错误）；内存地址确需整型表达时才允许 `long` 型，其他场景一律不可。
- `[MUST-9.2.4]` 禁止不同类型指针互相强制转换（继承关系除外）：`time_t *tpTmp = (time_t *)ipTmp;` 错误。

### 9.3 拷贝与边界

- `[MUST-9.3.1]` 内存拷贝前必须校验长度与指针，避免越界：`if ((NULL != pSrc) && (NULL != pDst) && (uiSrcLen <= uiDstCap)) { memcpy(pDst, pSrc, uiSrcLen); }`（`uiDstCap` 为目的缓冲真实容量，由调用方传入或通过 `sizeof` 得到）。
- `[MUST-9.3.2]` 禁用魔鬼数字计算字符长度：使用 `sizeof`、`strlen`、常量宏表达长度。

### 9.4 类与继承

- `[MUST-9.4.1]` 基类析构函数必须声明为 `virtual`（与 `[MUST-5.3.1]` 同一条，以 §5.3.1 为主出处，本条仅作内存章节交叉引用）。
- `[MUST-9.4.2]` 类中申请的成员内存必须在析构函数中释放，否则内存泄漏。
- `[MUST-9.4.3]` 多线程访问共享变量、函数、资源必须加锁（互斥量/自旋锁/读写锁），避免数据竞争与越界。

### 9.5 RAII 与资源管理

- `[SHOULD-9.5.1]` 鼓励 RAII 风格的"类封装 + 析构释放"：以显式类承担"申请/释放"职责，避免业务代码散落 `malloc`/`free`。典型结构：构造函数分配（失败置空）、析构释放并置空、禁用拷贝构造和赋值。完整样板见 `[MUST-9.5.2]`。
- `[MUST-9.5.2]` 拥有指针成员的类必须显式处理拷贝语义。三选一：深拷贝、禁用拷贝、仅允许移动（项目策略允许时）。**禁止**默认浅拷贝导致双重 `delete`。

**RAII + 禁用拷贝的标准样板**（受限 C++11 允许 `= delete`，见 §0.3）：

```cpp
class CBuffer
{
public:
    explicit CBuffer(xuint32_t uiSize);      // 构造分配 + 判空
    ~CBuffer(void);                           // 析构 delete[] 并置 NULL

private:
    CBuffer(const CBuffer &);                 // = delete; 亦可（允许）
    CBuffer &operator=(const CBuffer &);      // = delete; 亦可（允许）

    xuint8_t  *m_pData;
    xuint32_t  m_uiSize;
};
```

- **首选**：`= delete`（编译期即报错，错误信息更清晰）。
- **备选**：上例的"私有声明 + 不提供实现"（C++98 兼容风格），用于必须兼容更老编译器的模块。
- 同一文件内两种写法二选一，不得混用。

### 9.6 并发与线程安全

- `[MUST-9.6.1]` 共享可变数据必须加锁访问：多线程读写同一变量（含 `std::vector`/`std::map` 等容器）必须互斥；全体只读常量无需加锁。
- `[MUST-9.6.2]` 锁的持有范围必须最小化：持锁期间禁止执行耗时操作（IO、睡眠、阻塞调用）；持锁期间禁止调用可能再次加锁的函数（避免死锁）。
- `[MUST-9.6.3]` 使用作用域锁对象管理互斥量生命周期：通过构造加锁、析构解锁的 `CScopedLock`（或等价封装）确保所有退出路径都会解锁；禁止手工 `lock` 后散落多个 `unlock`。

```cpp
void CMyClass::Process(void)
{
    CScopedLock lock(m_mutex);
    // 临界区，函数退出自动解锁
}
```

- `[MUST-9.6.4]` 不同互斥量加锁顺序必须全局一致：多锁嵌套按固定顺序获取，避免循环依赖导致死锁。
- `[SHOULD-9.6.5]` 条件变量配合互斥量使用，用 `while` 而非 `if` 检查谓词：防止虚假唤醒（spurious wakeup）导致逻辑错误。

## 10. 变量、宏与常量

### 10.1 初始化

- `[MUST-10.1.1]` 严禁使用未初始化变量作为右值：局部变量定义时即初始化；结构体/类成员也应初始化；`std::string` 判空使用 `empty()`，禁止用 `c_str()` 判空。

```cpp
int flag = 0;                         // 必须初始化
switch (type)
{
    case 1:  flag = 1; break;
    case 2:  flag = 2; break;
    default: /* no action */ break;   // default 分支也要考虑 flag 取值
}
```

- `[MUST-10.1.2]` 循环变量必须初始化，防止随机值导致死循环（`unsigned char` 等小类型更易因溢出死循环）。

### 10.2 宏

- `[MUST-10.2.1]` 宏表达式定义最外层必须加括号，每个参数都要加括号：`#define MAX(a, b) (((a) > (b)) ? (a) : (b))`。
- `[MUST-10.2.2]` 多语句宏使用 `do { ... } while(0)` 结构：`#define DBG(x) do { printk("DBG: "); printk x; } while (0)`。
- 字符串字面量宏禁止使用多余括号，使用 `#define PATH_KEY "path/file"`，避免 `("path/file")` 风格


### 10.3 常量

- `[MUST-10.3.1]` 编译期常量**统一使用 `#define`**，命名全大写下划线分隔（`MAX_BUFFER_SIZE`、`DEFAULT_TIMEOUT`）；**禁止**用 `const int`/`static const int` 承担"命名常量"职责（与 §0.3 禁用 `constexpr` 保持同一风格基线）。`const` 的正当用途是"接口只读语义、成员只读访问"，详见 §16.1.2 / §16.1.4。
- `[SHOULD-10.3.2]` 同模块内多函数复用的编译期常量优先放在头文件集中定义（阈值、周期、容量、协议上限）；仅供单个 `*.cpp` 私有使用时保留在实现文件并保持最小可见范围（不以 `static` 为默认手段）。
- `[SHOULD-10.3.3]` `*.cpp` 私有宏/常量定义位置固定：`#include` 之后、函数实现之前；若需被头文件声明或多个翻译单元复用，则上移到 `*.h`（遵循 `[SHOULD-10.3.2]`）。

### 10.4 全局与静态变量

- `[SHOULD-10.4.1]` 全局变量尽量少用，必要时用 `g_` 前缀（见 §2.2.1）并集中在文件顶部声明、限定可见范围。
- `[SHOULD-10.4.2]` 静态变量默认不新增，确需使用时用 `s_` 前缀并在注释中说明必要性（配合 §8.4.2）。
- `[SHOULD-10.4.3]` 带"记忆"语义的 `static` 局部变量原则上避免，除非业务上确实必需；若使用，必须在注释中说明并发读写前提。

## 11. 字符串与数组

### 11.1 字符串处理

- `[MUST-11.1.1]` 字符串空间必须为 `\0` 预留位置。`strncpy` 拷贝到指定长度不会自动追加 `\0`，必须手工补齐。

```cpp
pMsgBuf = (xbyte_t *)malloc(BUF_SIZE + 1);
if (NULL == pMsgBuf) { return ERR_ALLOC; }
strncpy(pMsgBuf, strErrorMsg, BUF_SIZE);
pMsgBuf[BUF_SIZE] = '\0';
```

- `[MUST-11.1.2]` 字符串申请长度 = `strlen(src) + 1`；忘记 `+1` 会导致 `strcpy` 时 `\0` 越界（`malloc(strlen(dst) + 1)`）。
- `[MUST-11.1.3]` 字符串拷贝前确认目的空间足够：优先 `strncpy`/`snprintf` 并处理尾 `\0`；禁止无长度参数的 `strcpy`/`strcat` 用于不受控输入。
- `[SHOULD-11.1.4]` `std::string` 空串**首选默认构造** `std::string s;`（零成本、无字面量转换）；确需显式表达"空串语义"时可写 `std::string s("")`；禁止 `std::string s = "";`（存在潜在临时对象与拷贝）。

### 11.2 数组

- `[MUST-11.2.1]` 数组下标使用前必须做合法性判断：`while ((*pTmp != '-') && (i < (int)sizeof(sTmp) - 1)) { sTmp[i++] = *pTmp++; }` 随后 `sTmp[i] = '\0';`。
- `[MUST-11.2.2]` 数组容量按最大可能场景分配，避免运行时越界。
- `[MUST-11.2.3]` 字符数组清零用 `= {0}`；复合类型用 `memset`/`bzero`（`xbyte_t a[256] = {0};`；`memset(&stuAAA, 0, sizeof(stuAAA));`）。**注意**：结构体含类对象时不能用 `memset`/`bzero`，以免破坏虚表指针或导致非 POD 未构造状态。

### 11.3 字节序与对齐

- `[MUST-11.3.1]` 跨 CPU/分布式通信的数据结构必须显式处理字节序、位域与对齐：发送前主机序 → 网络序（如 `htonl`/`htons`），接收时执行反向转换。
- `[MUST-11.3.2]` 对外接口结构体（网络报文、文件落盘、共享内存、跨进程/跨模块 ABI）必须明确对齐策略（按协议或接口规范约定字节数），禁止依赖“当前编译器默认行为”。
- `[MUST-11.3.3]` 结构体包含 `xuint8_t`/`xbyte_t` 等窄字段且存在尾部补齐风险时，必须显式声明保留字段（如 `reserved[]`），禁止将编译器隐式 padding 当作业务字段或协议空间。
- `[MUST-11.3.4]` 禁止将 `#pragma pack(1)` 作为默认对齐手段。仅当第三方协议/硬件寄存器布局强制要求时可局部使用，并且必须限定最小作用域、补充风险注释（未对齐访问/性能），并在使用后配对恢复默认对齐。
- `[SHOULD-11.3.5]` 在不改变语义前提下，结构体成员建议按对齐需求从大到小组织（如 `xuint64_t` → `xuint32_t` → `xuint16_t` → `xuint8_t`），以降低补齐空间和跨平台差异风险。
- `[SHOULD-11.3.6]` 结构体对齐细则请参考 `struct-memory-alignment.mdc`。

## 12. 类型与强制转换

### 12.1 类型定义

- `[MUST-12.1.1]` 基本变量类型统一使用重定义名（类型映射见 `streamaxtype.h`）：

| 原始类型 | 重定义类型 |
|----|---|
| `signed long long` / `unsigned long long` | `xint64_t` / `xuint64_t` |
| `float` / `double` | `xsingle_t` / `xdouble_t` |
| `signed int` / `unsigned int` | `xint32_t` / `xuint32_t` |
| `signed short` / `unsigned short` | `xint16_t` / `xuint16_t` |
| `signed char` / `unsigned char` / `char` | `xint8_t` / `xuint8_t` / `xbyte_t` |
| `void *` | `xhandle_t` 或 `xpvoid_t` |
| `xuint32_t` / `xuint64_t`（时间戳） | `xtime32_t` / `xtime64_t` |

- `[MUST-12.1.2]` 禁止使用 `long`。例外：仅当表达内存地址时允许。
- `[SHOULD-12.1.3]` 推荐使用带明确长度的类型（如 `xint32_t`、`xuint64_t`），避免平台字长差异。
- `[SHOULD-12.1.4]` 结构体定义风格优先使用匿名 `struct` + `typedef` 形式：`typedef struct { ... } Xxx_t;`。除前向声明或与第三方 ABI 对齐等特殊场景外；新代码与重构代码均优先沿用项目既有风格。

### 12.2 强制转换

- `[MUST-12.2.1]` 类型强制转换必须防止越界：小类型容纳大类型、有符号/无符号互转、截断等场景均需校验。
- `[MUST-12.2.2]` 禁止 `int` 与指针互转（见 `[MUST-9.2.3]`）。
- `[MUST-12.2.3]` 禁止不同类型指针互相强制转换（见 `[MUST-9.2.4]`）。
- `[SHOULD-12.2.4]` C++ 文件中优先使用 C++ 风格强转：`static_cast` / `const_cast` / `reinterpret_cast`，避免 C 风格 `(T)x`。
  - `static_cast`：数值类型/有继承关系的指针/引用之间的安全转换；须按 `[MUST-12.2.1]` 校验越界。
  - `const_cast`：仅限修正既有接口的 `const` 缺失（过渡手段，后续按 §16.1.4 调整接口）。
  - `reinterpret_cast`：仅限字节层面的协议拼/解包与内存映射；禁止随意使用。
  - **禁用** `dynamic_cast`（依赖 RTTI 与异常语义，与 §0.3 冲突）。
  - `extern "C"` 接口或为兼容既有 C 代码的场景保留 C 风格强转。

### 12.3 溢出保护

- `[MUST-12.3.1]` 加、减、乘等运算必须做溢出保护。典型错误：`for (unsigned int i = 0; i <= (len - 1); i++)` 在 `len == 0` 时 `len-1` 变成极大值；正确做法先判 `if (len > 0U)` 再 `for (i = 0U; i < len; i++)`。
- `[MUST-12.3.2]` 除法必须对"除零"做有效保护：`if (0 == divisor) { return ERR_DIV_ZERO; } result = dividend / divisor;`。

## 13. 代码复杂度

### 13.1 度量

- `[MUST-13.1.1]` 函数最大嵌套深度 ≤ 5。最外层深度为 0；遇 `if`、`else`、`while`、`for`、`switch/case`、`&&`/`||` 复合判断均计入深度。
- `[MUST-13.1.2]` 函数最大圈复杂度 ≤ 20。推荐使用 SonarQube 等工具度量。

### 13.2 降复杂度实践（建议，非强制）

> 本节为超过 `[MUST-13.1.1]` / `[MUST-13.1.2]` 阈值时的推荐重构手法，不单独作为门禁规则。

1. **提炼函数**：重复逻辑拆为小函数，避免"超长函数"。
2. **简化条件**：分解复杂 `if`、合并同结果分支、提炼重复条件表达式。
3. **职责分离**：查询与设置分离，参数化公共路径。
4. **多态替代**：大规模 `switch`/`if` 分发可用多态。
5. **Early-return / Guard Clause**：提前拒绝异常输入，降低嵌套（示例见 §8.3.4）。

## 14. 打印与日志

### 14.1 频率控制

- `[MUST-14.1.1]` 相同内容打印间隔必须大于 1 秒，避免日志刷屏；严格符合打印等级（DEBUG/MESSAGE/WARNING/CRITICAL/ERROR）语义。

### 14.2 格式字符串

- `[MUST-14.2.1]` 打印格式符必须与变量类型严格匹配：

| 变量类型 | 打印格式符 |
|----|-----|
| `xint64_t` / `xuint64_t` | `%lld` / `%llu` |
| `xsingle_t` / `xdouble_t` | `%f` / `%lf` |
| `xint32_t` | `%d` |
| `xuint32_t` | `%u` |
| `xint16_t` / `xint8_t` | `%d`（依赖默认参数提升，严格模式下分别使用 `%hd` / `%hhd`） |
| `xuint16_t` / `xuint8_t` | `%u`（严格模式下分别使用 `%hu` / `%hhu`） |
| `xbyte_t` | `%c` |
| 字符串（C 风格 / `std::string::c_str()`） | `%s` |
| 指针 | `%p` |

类型不匹配可能导致打印异常甚至崩溃。若编译开启 `-Wformat=2`，必须使用上述严格形态。

- `[MUST-14.2.2]` 打印指针必须使用 `%p`：`printf("this[%p]\n", this);`。

### 14.3 日志封装

若项目提供统一日志宏（例如 `RM_CBB_LOG_XXX`，例如 `BUS_LOG_XXX`），优先使用以获得编译期检查与日志治理能力（等级、限流、上下文字段等）。

### 14.4 日志与线程安全

- `[MUST-14.4.1]` 多线程打印必须使用线程安全的日志接口：禁止在多线程代码中直接调用 `printf`/`fprintf`/`std::cout` 拼装跨调用的多段输出（单次原子调用仍受 C 库保护）；必须调用产品线统一的日志宏（例如 `RM_CBB_LOG_XXX`，例如 `BUS_LOG_XXX`）；日志宏至少应满足线程安全、等级分层(DEBUG/MESSAGE/WARNING/CRITICAL/ERROR)。

## 15. 输入输出与编译器

### 15.1 输入输出

- `[SHOULD-15.1.1]` 避免使用 `scanf`。格式符与参数类型不匹配时极易越界写；如必须使用，严格区分 32/64 位平台整数长度。

### 15.2 编译选项

- `[MUST-15.2.1]` 动态链接库必须加 `-fPIC`。
- `[MUST-15.2.2]` GCC 必须开启 64 位相关警告。至少开启：`-Wlong-long`、`-Wformat`、`-Wpointer-arith`，及时处理所有相关 warning。

### 15.3 平台差异

- `[MUST-15.3.1]` 类 Unix 平台优先使用项目统一宏 `_posix_` 区分；该宏由项目构建系统在 Unix/类 Unix 目标编译时定义（**非 C/C++ 标准宏**，不依赖 `__unix__` / `_POSIX_VERSION` 等平台实现宏，以避免交叉编译期差异）。新代码在条件编译时一律使用本宏，不得改用标准宏或自造新宏。

```cpp
#ifdef _posix_
    #include <unistd.h>
    #include <sys/types.h>
#else
    // 其他系统代码
#endif
```

## 16. 其他实践建议

### 16.1 迭代器与 `const` 使用

- `[SHOULD-16.1.1]` 通过迭代器访问对象成员时注意优先级。`*` 的优先级低于 `->`：`*it->pField` 会被解析为 `*(it->pField)`（先解 `it` 的成员再解引用），若本意是"先对 `it` 解引用再访问成员"，必须加括号写作 `(*it).pField`（或直接写 `it->pField`）。**反例**：`*it->pData[0]` → 实际等价于 `*(it->pData[0])`，与预期不符；**正例**：`it->pData[0]` 或 `(*it).pData[0]`。
- `[SHOULD-16.1.2]` `const` 使用最小化：优先用于接口只读语义（输入参数、只读成员访问）与边界约束变量；不以“局部变量全部加 `const`”为目标。
- `[SHOULD-16.1.3]` 局部临时变量默认不加 `const`：仅一次性透传、不会复用、不会参与边界判断的短生命周期中间值（如循环内读取配置后立即 `insert`）不要求 `const`；仅当变量需要跨多处使用、参与边界校验或必须表达“不可变语义”时，才建议加 `const`。
- `[MUST-16.1.4]` 输入指针参数若仅用于读取，必须在类型前加 `const`（见 `[MUST-8.1.3]`）。
- `[SHOULD-16.1.5]` 输入对象按值传递时，宜改为 `const &`（见 `[SHOULD-8.1.4]`）。
- `[SHOULD-16.1.6]` 除明确的打印函数外禁止自定义不定参函数（见 `[MUST-8.1.7]`，`va_list` 难以类型检查）。
- `[SHOULD-16.1.7]` 类成员函数默认不使用尾置 `const`（`foo() const`）以保持项目统一风格；

### 16.2 错误处理实践

- `[MUST-16.2.1]` 错误码与正常值分离返回：函数只返回错误码；输出值通过输出参数（指针/引用）返回。错误码在 `streamaxerr.h` 中集中定义；禁止函数内私自定义"魔数"错误码。

```cpp
xint32_t GetDeviceId(xuint32_t uiIndex, xuint32_t *pOutId)
{
    if (NULL == pOutId)              { return ERR_INVALID; }
    if (uiIndex >= MAX_DEVICE_COUNT) { return ERR_OUT_OF_RANGE; }
    *pOutId = g_deviceTable[uiIndex].uiId;
    return ERR_OK;
}
```

- `[MUST-16.2.2]` 错误返回路径必须释放已申请资源：任意一个错误分支遗漏 `free`/`delete`/`close` 都视为不合规。
- `[SHOULD-16.2.3]` 使用 `do { ... } while(0)` 收敛错误处理：集中管理资源释放，取代 `goto`。进入 `do` 前初始化资源指针为 `NULL`，任一步失败 `break`，在 `while(0)` 之后集中检查并释放。
- `[SHOULD-16.2.4]` 对有意义的返回值函数（如 `memset`、`memcpy`、`snprintf`）不使用 `(void)func(...)` 形式做"忽略返回值"抑制。若确实不关心返回值，优先直接调用并通过代码上下文体现意图；若返回值与安全性相关（长度、截断、错误码），必须显式校验并处理。

```cpp
xint32_t  iRet  = ERR_FAIL;
xuint8_t *pBuf = NULL;
do
{
    if ((NULL == pData) || (0U == uiLen)) { iRet = ERR_INVALID; break; }
    pBuf = new(std::nothrow) xuint8_t[uiLen];
    if (NULL == pBuf) { iRet = ERR_ALLOC; break; }
    // 业务处理
    iRet = ERR_OK;
} while (0);

if (NULL != pBuf) { delete[] pBuf; pBuf = NULL; }
return iRet;
```

### 16.3 枚举与魔数

- `[MUST-16.3.1]` 禁止在业务代码中出现魔数；用具名常量或枚举承载含义。反例：`if (type == 3) { ... }` / `char buf[128];`；正确：`#define MAX_NAME_LEN 128; if (eDEV_TYPE_GATEWAY == type) { ... } char buf[MAX_NAME_LEN];`。
- `[MUST-16.3.2]` 枚举值显式赋值：所有枚举首值必须显式赋值；非递增处必须显式赋值，便于跨模块通信/序列化稳定。

## 17. 规则例外与团队协作

- **原则**：前述规则基本强制；允许有限例外，但任何例外必须**显式记录**，不得悄悄破例。
- **既有非一致代码**：修改历史代码时**局部一致性优先**，保持该文件既有风格；不对文件做大规模风格改写，除非整体统一经过团队评审。
- **第三方库集成**：在 `extern "C" { ... }` 或隔离模块内允许沿用第三方风格；封装层必须符合本规范，向业务代码暴露符合项目规范的接口。
- **兼容性条件编译**：使用 `#ifdef LEGACY_COMPILER / #else / #endif` 明确兼容边界；禁止在业务代码中散落大量条件分支。
- **例外决策流程**：评估影响 → 团队评审 → 文档记录（在代码注释中引用具体规则编号） → 每迭代复核。
